# 面向 Agent 接手的项目知识库：文档系统设计方案

> 状态：设计稿（已实现 · Phase 1~6 落地于独立仓库 `<repo>`，通用、与任何项目解耦）
> 目标受众：接手**任意目标项目**的新 Agent；人类为可选读者（本系统为通用系统，目标项目仅为示例）
> 设计约束：先定架构与流程，**不绑定具体文档内容**；后续实施阶段再填充真实数据。
> **适用范围（重要）**：本方案描述一个**通用的、从零构建的项目知识库文档系统**，**不耦合任何特定项目**（如 Hermes）。文中出现的 `agent/` `apps/` `gateway/` 等目录与『Hermes』字样仅作**示意目标项目**的示例；所有项目结构、语言、触发方式、治理规则均通过 `config.yaml` 配置，**不硬编码到系统**。

### 0.4 术语速查（最容易混的，忘了查这里）
| 词 | 意思 |
|---|---|
| **三件套** | 检索接口每个符号都返回：`向量`（相似度）+ `注释`（`@domain` 显式键）+ `注释文本`（docstring / 可读 note）；再加 `向量近邻`（最近的前 N 个符号） |
| **两方向并行** | 文本生成方向（TypeDoc / Storybook / Ladle）⇄ 向量智能方向，**地位平等、互不为主** |
| **Domain 框架** | = 文本方向的可读产出 + 向量方向的归因/检索，并列服务于同一能力域 |
| **catalog 快照** | 提取后落盘的元数据（符号→域 + 来源 + 置信度），渲染读快照、与向量快照同源 |
| **四种「索引」** | `llms.txt`=结构/位置/token成本；向量索引=语义坐标；catalog=域归属；全文倒排=词项。**都是派生指针，不是原始信息**（原始=源码/docstring/`@domain`/注释文本） |
| **三态 T0/T1/T2** | 零人（默认）/ 一人+N Agent / 有人类团队；共用同一 AI 核心 |
| **CI / git hook** | CI=持续集成，远端公共机自动跑「构建→校验→发布」（字母 I）；git hook=commit/push 瞬间触发的本地脚本 |
| **active / v_next** | `active`=对外唯一真相（Agent 实际读到的那份）；新版本先在 `v_next` 构建、校验过才原子切换 |
| **fail-closed / unresolved** | 低置信且无人可升级时：不裁决、保留旧 `active`、该项标 `unresolved` 冻结、两侧材料原样并列给下游 Agent |
| **永久冻结**（待拍板③选项） | `unresolved` 项**不按时间重试**，一直冻结到「**外部条件变化**」才唤醒重裁——模型升级 / 新证据 / 代码变更 / 人层开启。事件驱动。省算力、文档零抖动；风险是若无事件可能永远沉睡，需「冻结项滞留时长」KPI 兜底（§14.6 #10） |
| **TTL**（待拍板③选项） | **Time To Live**（存活时长），网络/缓存术语（DNS、缓存记录的寿命），到期即失效并重新验证。此处指给 `unresolved` 项设一个复查周期 t，每到期就**自动重新裁决一次**，时间驱动。好处是一定会自愈、不会永久遗漏；风险是空转重算（代码没动却反复跑 jury），需加退避/重试上限/内容哈希门。折中方案：**混合**——事件驱动为主 + 长 TTL 兜底（只在"滞留超阈值"时才唤醒） |
| **宪法两层 / jury / dissent** | 不可变核心 + 可修订层；陪审团（≥2 **异构**模型）；**异议强制可见** |
| **结构性不自审** | 用户定调：`提议者 ≠ 审核者`。宪法核心不靠"AI 碰不到的外部硬约束"守护，而靠「多个异构审核 AI + 严格提示词 + 身份分离」——**全 AI 闭环、无外部例外**。风险根因是「同一个 AI 自己审自己」，不是"规则会被改" |
| **Scheme C / D** | 见 0.5 |

### 0.5 当前主路线 = **C（零人基线）+ D（可选人层）**，二者叠加、不是二选一
- **C = 「零人全自主 + 结构性不自审 + fail-closed」**：定义**系统内部在没有任何人时怎么自治**。六件：① 宪法两层（不可变核心 + 走 typed amendment 的可修订层），**核心由异构审核群守护**（提议者≠审核者 + 严格提示词），不是靠"AI 碰不到的外部硬约束"；② 裁决层（jury + judge 出裁决/置信度/dissent）；③ 无升级目标时 fail-closed 四步兜底；④ 非 Agent 的外部健康探针；⑤ 人层可选默认关；⑥ 只承诺「有界可测可审计」，不承诺永不犯错。详见 §14.5。
- **D = 「三态可切换」**：定义**有人时怎么把人挂上去**。T0/T1/T2 共用同一套 AI 核心，人只是可插拔外挂层，`config.yaml` 开关、人层永远默认关；绝不出现「某功能只有有人在才能跑」。§14.4 把 C、D 并列只是为了分别审优缺点。
- **为什么 C 长这么复杂**：三层防御各治一个零人特有的坑——AI 自改规则会悄悄放宽自己（Ouroboros 自保条款）→ 用**结构性不自审**治；没人可升级（旧方案 C 的死穴）→ 用 **fail-closed** 治；系统全停没人发现（CTE 13.5 天事件）→ 用**外部探针**治。

## 1. 目标与成功标准

**最终目标**：让一个对目标项目一无所知的新 Agent，在最短时间内建立完整、准确的项目心智模型，并能可靠地定位代码、评估改动影响、遵循项目约定。

**Agent 应能回答的核心问题**：
- 这个项目由哪些**能力域**构成？每个域负责什么？
- 某个能力（如"计费""上下文压缩""浏览器驱动"）落在哪个模块？
- 改某个模块**会影响什么**（上游/下游）？
- 系统的**入口点**在哪（CLI / gateway / TUI / desktop）？从入口怎么顺藤摸瓜？
- 项目有哪些**硬约束/约定**（配置 vs 环境变量、secrets 规则、缓存不变性、核心窄腰原则）？

**成功标准（可检验）**：
- 存在一份"自顶向下"的项目地图，从总览可逐层下钻到任意源码文件。
- 任意模块都能查到：一句话职责、所属域、依赖关系、入口标识。
- 提供"改 X 影响什么"的依赖/调用图直达答案。
- 文档与代码失同步时有可见的维护机制。

## 2. 现状资产与缺口

### 现有资产
- `AGENTS.md`：项目意图层与贡献准则（核心窄腰、缓存神圣、扩展而非复制等）。**是准则，不是地图**。
- `docs/generated/`：89 个 per-file API 参考（agent/ 60 + scripts/ 9），含路径、大小、Functions & Classes。扁平、无层次、无关联。
- `wiki/`：46 个主题化笔记（编译发行、架构方案、上下文系统、NAS与子代理、勘察审计、其他专题）。有深度但无统一入口与结构化索引。
- `docs/` 其他子类：design / plans / contracts / i18n / observability / security / kanban / middleware / rca。
- `reports/`：12 个交付/审计报告。

### 缺口（正是文档树要补的）
1. **无自顶向下的项目地图**：能力域 → 模块的层次缺失。
2. **generated 扁平无归类**：89 个文件同名感强，无域归属、无相互关联。
3. **wiki 有主题无导航**：内容分散，缺统一索引与入口。
4. **缺横切视图**：模块依赖/调用关系、术语表、入口点清单、约定速查均未固化。
5. **可能失同步**：文档随代码演进会腐化，无机制保证新鲜度。

## 3. 设计原则

- **【元原则 · 覆盖全稿 8 条主线 · 优先级最高】AI 全自主为默认，人类为可选附加，零人亦须成立**：系统必须能在**完全没有人类**的情况下跑完"生成 → 归因 → 裁决 → 维护 → 验收"全闭环。任何时候出现「交人 / 人工 / 人类团队介入」的依赖，都**必须同时存在一条不依赖人的默认路径**；人只作为 `config.yaml` 可开启的附加层（默认关）。这条推翻原稿以人为隐含前提的一切表述，详见 §14。
- **分层下钻**：概览 → 能力域 → 模块 → 代码叶子。每层可点击穿透。
- **溯源优先**：每个抽象节点都必须能下钻到原始文件/文档，不凭空创造信息。
- **双形态输出**：同时产出**机器可读索引**（JSON/YAML，供 Agent 直接读取）与**人读导航树**（MD / HTML / MkDocs）。
- **增量维护**：变更触发局部重算，而非整体重建；带版本戳与新鲜度标识。
- **复用而非重建**：以 AGENTS.md、wiki、generated 为数据源，文档系统做"编织与索引"，不重复造内容。
- **渐进披露 / Token 预算优先**：浅层只给"地图与摘要"，深层才给细节。Agent 阅读时**先看表层把握布局，再按需深入某一个模块**，避免一次性灌入全部内容、浪费 context 窗口。
- **Agent 第一读者，人类可选读者**：产物**首先对 Agent 负责**（机器可读索引、可逐页拉取、可裁决）。同源产物兼顾人读（MkDocs HTML）是"免费附赠"而非硬约束；零人场景下人读增强（美观 / demo / 站内搜索 / TypeDoc HTML 站）全部默认关、永不成为必需。原「人类 + Agent 双读者通用」按元原则降级——不再是"通用硬约束"。

## 4. 文档树的层次模型

```
L0  项目总览 (Overview)
    ├─ 一句话定位 + 顶层能力域列表
    ├─ 如何导航（阅读顺序建议）
    └─ 关键约定指针（指向 AGENTS.md / 约定速查）

L1  能力域 (Capability Domains)         ← 项目的"骨架"
    ├─ 域职责（一段话）
    ├─ 包含模块清单
    ├─ 域间关系 / 关键数据流
    └─ 域级陷阱与边界

L2  模块页 (Module Pages)               ← 每个 .py 一个节点
    ├─ 一句话摘要
    ├─ 关键 API（签名级）
    ├─ 依赖的域/模块、被谁依赖
    ├─ 入口标识（是否为 CLI 命令 / 服务 / 工具）
    └─ 下钻 → L3

L3  代码叶子 (Code Leaf)
    └─ 复用 docs/generated 原始文档（不重写）

横切索引 (Cross-cutting)
    ├─ 术语表 glossary
    ├─ 入口点清单 entrypoints
    ├─ 约定速查 conventions（配置 vs env、secrets 规则…）
    └─ 依赖/调用图 dependency-graph
```

## 5. 系统流程（Pipeline）：系统要怎么做

| 阶段 | 名称 | 输入 | 输出 | 说明 |
|------|------|------|------|------|
| 1 | 采集 Harvest | 源码树、`docs/`、`wiki/`、`AGENTS.md` | 文件清单 | 全量+增量两种触发 |
| 2 | 抽取 Extract | 每个源码文件 | 元数据（docstring、签名、类、import 依赖、入口标记） | 静态解析为主 |
| 3 | 分类 Classify | 元数据 + 路径/命名规则 | 分类映射表（文件→能力域） | 规则优先，LLM 辅助兜底 |
| 4 | 摘要 Summarize | 元数据 + docstring | 模块一句话摘要、域概述 | 可自动提取，可人工润色 |
| 5 | 关联 Relate | 依赖 + 调用关系 | 模块依赖图、数据流向 | 回答"改 X 影响什么" |
| 6 | 渲染 Render | 上述全部 | 机器可读 index + 人读树 | 形态可配（见 §8） |
| 7 | 维护 Maintain | git diff / CI 事件 | 增量更新 + 新鲜度戳 | 链接校验、失效标记 |

**数据流**：源码/文档 → Harvest → Extract →（Classify → Summarize → Relate 可并行）→ Render → 产物；Maintain 回环监控变更。

## 7. 现成文档系统调研（GitHub）

> 目的：避免凭空设计，先看社区成熟方案。结论：**MkDocs Material + mkdocstrings 做"可点开深入的树"，llms.txt 做"Agent 表层索引"**，两者同源生成，最契合本项目（Python 为主、要树状可折叠、人类+Agent 通用、省 Token）。

| 方案 | 形态 | 树/折叠 | 自动 API 文档 | 人类友好 | Agent 友好 | 备注 |
|------|------|---------|--------------|----------|------------|------|
| **MkDocs Material + mkdocstrings** | 静态站 | 侧边栏**可折叠树** | `:::` 从 docstring 自动生成 | ★★★ 美观、搜索、Mermaid | 可配 llms.txt / 逐页拉取 | **推荐主形态** |
| **llms.txt**（标准，非生成器） | 根目录索引 | — | — | 不直接看 | ★★★ 精简目录+链接，<10k tokens 把握全布局、按需深入 | **推荐给 Agent 的表层入口** |
| pdoc | 静态站 | 模块树 | 自动 | ★★ 偏纯 API 参考 | 可拉取 | 轻量但无主题化地图 |
| VitePress / Docusaurus | 静态站(Vue/React) | 侧边栏树 | 需插件 | ★★★ | 可拉取 | 功能全但偏重，需前端栈 |
| mdBook / Starlight(Astro) | 静态站 | 树 | 弱 | ★★ 书本式 | 可拉取 | 轻量，非 API 自动 |
| Docsify | 运行时渲染 | 树 | 否 | ★★ 无构建 | 弱(JS 渲染) | 不 SEO |
| Sphinx + autodoc | 静态站 | 否(页面) | 自动(reST) | ★★ 配置重 | 可拉取 | 老牌 Python，但 reST 门槛 |

**对你两种直觉形态的覆盖**：
- "可点开深入看详情的树" → MkDocs Material 的**可折叠侧边栏树**（能力域 → 模块 → 代码详情）。
- "README 里可展开看详情" → 零依赖备选：用 `<details>` 生成可折叠 README 树；或 MkDocs 站点本身即更优解。
- "表层快速把握布局 + 深入小模块" → **llms.txt**（几千 token 给全貌与链接）+ MkDocs 深层页（点击进入）。

## 8. 让 Agent「更快接手」的关键增强（区别于普通文档）

普通文档只是"信息罗列"。本系统针对 **人类 + Agent 双读者** 做以下增强：

1. **入口点优先**：明确 CLI / gateway / TUI / desktop 入口，让接手者从入口顺藤摸瓜而非盲搜。
2. **影响面直答**：依赖/调用图直接回答"改 X 影响什么"，降低误改风险。
3. **约定速查**：把 AGENTS.md 的硬约束（配置走 `config.yaml`、secrets 走 `.env`、prompt 缓存跨轮不变、核心窄腰）压缩成速查卡。
4. **边界/陷阱清单**：从 wiki 审计笔记抽取"不要做什么"，前置给接手者。
5. **地图优先于细节（渐进披露）**：表层只给能力域地图 + 一句话摘要；深入按需发生，保护 Agent 的 context 预算（呼应 §3）。
6. **llms.txt 表层索引**：给 Agent 一个根目录精简索引（站点名、一句话定位、各页链接+描述），Agent 先读它把握全布局，再只拉取相关深层页——**这是省 Token 的关键机制**，优于一次性喂全文或读 INDEX.json。
7. **每页自包含 + 稳定锚点**：每页讲清一个概念，标题即主题，便于检索与引用（遵循 llms.txt 最佳实践）。
8. **动态刷新（Agent 运行时贡献）**：文档不是一次性产物。Agent 在执行任务过程中顺带分析代码、刷新依赖图与模块摘要，使文档随真实使用持续保鲜——既减轻静态生成滞后，又契合"Agent 接手即贡献"的闭环。

## 11. 前端 / TS / Apps 文档化策略（独立课题）

> 本课题单列：TS/Apps 的"文档单元"不是文件而是符号/组件/App，是整套文档系统真正的难点。以下为基于外部调研的分阶段设计，非一次性定案。

### 11.1 核心洞察
- 文档单元三层：符号（导出符号/类型/Hook）、组件（UI+状态）、App（入口应用）。
- App 作为入口应用（非被 import 的库），**不写 API 参考页**，产出应为：能力清单 + 路由表 + 依赖图。
- Python 侧 mkdocstrings 够用；难点全在 TS/Apps。

### 11.2 三层拆解
| 层 | 问什么 | 文档单元 | 典型产物 |
|----|--------|----------|----------|
| 符号层 | 这个函数/Hook/类型怎么调 | 导出符号 | Props 表、签名、继承链 |
| 组件层 | UI 长啥样/状态 | 组件+story | 可交互 demo、视觉回归 |
| 应用层(App) | 提供什么能力/入口/依赖 | 整个 App | 路由表、能力清单、依赖图 |

### 11.3 六套方案对比
- **A. TypeDoc + typedoc-plugin-markdown → 喂 MkDocs**：TS 侧最成熟；类型即文档；产物标准 MD；可出 Props 表。缺点：默认按文件层级易深碎；业务语义(`@domain`)需自定义 TSDoc 标签+后处理；大仓慢。→ **阶段一主力推荐**。
- **B. Storybook(`--docs`) 独立站**：交互 demo、addon-docs 自动 props；设计可看。缺点：HTML 产物 Agent 读不到；配置升级成本高；冷启慢；组件隔离掩盖集成 bug。→ 仅真需 demo 时上。
- **C. Ladle / Dumi 轻量替代**：Ladle(React-only, 快)；Dumi(中文友好组件门户)。→ 过渡/轻量。
- **D. react-docgen-typescript 自写脚本取表**：极轻、可控、可加"归属能力域"列。缺点：只管 props。→ 适合"只要可索引表"。
- **E. ts-morph 自定义提取**：唯一能把"代码块属哪个能力域"做扎实；符号级粒度；可产 Agent 索引+人类文档+breaking change 检测。缺点：开发成本最高。→ 作 A/D 增强层而非起点。
- **F. Backstage Catalog**：关系与目录解耦、多语言统一建模、支持反向查询。缺点：平台级投入重、清单需同步。→ 对单体 repo 太重，思想轻量化借用。

### 11.4 多个代码块如何关联（三解法，按成本）
1. **锚点 ID + 片段复用**（最低成本）：显式锚点 `## X {#x}`（必须显式，别靠自动）+ snippets 插件复用公共示例。
2. **清单文件 manifest**（轻量 Backstage，最推荐）：每域一个 `index.json`/`catalog.yaml`（机器可读），`ts-morph` 脚本从源码反哺，pre-commit 跑。文档是视图，清单是真相；归属不再由文件位置决定。
3. **交叉引用**（mkdocs-autorefs）：`[X][]` 跨页链符号，配合清单 id 形成可遍历图。

### 11.5 nav 自动化
- `mkdocs-literate-nav`：SUMMARY.md 替代 YAML，通配符兜底。
- `mkdocs-section-index`：section 自身可点击，配 `navigation.indexes`，对上每域入口页。
- `mkdocs-monorepo-plugin`：`!include` 合并多导航树（若 Apps 拆仓）。
- **兜底**：脚本扫描 docs/ + 清单，自动生成各域 `index.md`（模块表 + Mermaid 依赖图），pre-commit 执行，nav 永不脱节。

### 11.6 分阶段实施
- **阶段一（先走通）**：TS 侧方案 A（typedoc-plugin-markdown + frontmatter），产物进 `docs/api/ts/`，`.gitignore`，CI 生成；关联解法1；nav：literate-nav + 通配符兜底。
- **阶段二（归属打架时）**：上解法2（清单）+ 几十行 ts-morph 抽 `@domain` 标签；脚本顺带生成 Mermaid 依赖图。
- **阶段三（需 demo 时）**：方案 C（Ladle）优先于 B，挂子目录，保留 Markdown 版给 Agent。
- **永远不做**：给 App 写 API 参考页。App 只配一页"能力清单+路由表+依赖图"。

### 11.7 Agent 视角注意事项
- 控制生成粒度：避免单个上万行文件；挑支持"按模块拆分输出 + master index"的工具，否则返工。
- `exclude_docs`：reports/、api/ 等生成物排除在搜索外，避免污染检索。

### 11.8 待定决策（逐项商量）
- 阶段一 TS 工具链：✅ **文本方向 = TypeDoc(A) 为主 + 借用 B(Storybook 交互 demo) 与 C(Ladle/Dumi 轻量 demo) 的思路**（用户定）。D/E 的"归属抽取"职责已由 §12 向量隐式轨接走，文本方向不再重复做归类，专注可读文档 + demo/可视化。
- 阶段二归属抽取机制：✅ **主线=纯 TSDoc `@domain` 标签 + markdown 后处理**（最小侵入、复用 A 产物）；**补充=ts-morph(E) 作可选增强层**（符号级粒度、反哺清单、可 breaking 检测）。（自主定，理由见正文）
- `@domain` 标签规范：✅ **自定义 TSDoc 标签 `@domain`，值=规范英文域键，多域用逗号分隔**（自主定，理由见下）。
  - 规范英文域键（canonical keys，如 `billing` / `context-compression` / `model-adapter`）集中定义在单一 schema 文件（`docs/kb/_meta/domains.json`）作为唯一真相源；抽取器据此校验并告警未知域（借用"每域独立标签"方案的防拼写错思路，但不膨胀标签数）。
  - 在 `tsconfig` 的 typedocOptions / `tsdoc.json` 声明该自定义标签，避免 linter 报 unknown tag（借用 `@category` 复用方案的零摩擦注册思路）。
  - 示例：`/** @domain billing, accounts - 计费与账户域 */`（逗号分隔支持跨域多重归属）。
- 清单格式：✅ **两者都产**（index.json 喂机器 + catalog.yaml 供人看）。
- 前端产物 git 策略：✅ **.gitignore + CI 生成**（仓库干净、与代码同步）。
- 注：上述 `@domain` 单一键是**向量双轨中的"显式轨"**；与其并行的"隐式轨"（Embedding 相似度自动归因）见 §12。

## 12. 向量智能层（语义归因 + 语义检索，与文本生成层并行）

> 用户提出的范式性补充：标注在 1439 文件级不可持续（标注债务、拼写、域漂移）。用 Embedding 把"符号/模块"映射到语义空间，以相似度解决多域重归属、语义混淆、注释容差。本层与"纯文本生成层（TypeDoc 为主 + Storybook/Ladle 演示）"作为**两大地位平等的主要方向同时并行，互不为主**。

### 12.1 两个主要方向并行（地位平等，互不为主）
- **方向一 · 向量智能层**：负责"符号/模块 → 能力域"的**软归因**（相似度分布，而非硬标签）+ **语义检索**（Agent 问"计费逻辑在哪"直接语义命中，无需精确标注）。
- **方向二 · 纯文本生成层**：以 TypeDoc(A) 产出人/Agent 可读的 Markdown 页（域 landing、模块页、API 参考），并按需借 Storybook(B) / Ladle-Dumi(C) 做组件 demo 与可视化。**两方向地位平等**，文本层不是向量的"补充"，向量层也不是文本层的"增强"；各司其职、并行产出。
- **Domain 框架含文本工具**：每个能力域的文档由文本方向通过 TypeDoc/Storybook/Ladle 落地（可读页 + demo），归因由方向一的向量与显式键共同给出（见 §12.2/§12.6）。即 **Domain = 文本方向的可读产出 + 向量方向的归因/检索**，两者并列服务于同一域。
- 二者分工：向量**不直接产散文**，而是喂给结构化 catalog（符号→域 + 相似度分）；文本层**消费 catalog** 出可读页。catalog 中"键 / 向量 / 两者一致"的来源标记仅用于追溯，不代表某方权重更高。

### 12.2 归因双轨（显式键 ⇄ 向量，地位平等）
- **显式轨（单一键）**：开发者写的 `@domain <键>`（§11.8），crisp、可审查、零歧义——属人工信号。
- **隐式轨（向量）**：Embedding 相似度，对未标注/标注不全的符号**自动建议归属**（软分布），并暴露域间语义梯度——属机器信号。
- **两者地位平等，互不为主**：不是"键是真相源、向量兜底"，也不是"向量默认、键覆盖"。任一单方面出现时它说了算；**两者都出现且结论冲突时，不自动偏向任一方，而是标记 `conflict` 交人工裁决**（见 §12.6）。

### 12.3 向量能解决 / 不能解决（诚实边界）
- ✅ **注释容差**：不依赖精确标注即可归因，天然容忍漏标/错标/措辞差异。
- ✅ **多域重归属**：相似度产出"0.7 billing + 0.3 accounts"的软成员分布，比硬标签更诚实。
- ✅ **语义混淆（暴露）**：两域语义重叠时，向量**显现**梯度，提示人工 taxonomy 在何处模糊——但**不裁决**，仍需阈值/人工确认。
- ⚠️ **不消除种子标注**：每域仍需少量手工 seed（代表符号）定义质心；向量把"每符号一标"降到"每域几标"，不是零标注。
- ⚠️ **确定性风险**：相似度随 Embedding 模型/语料变化会漂移；onboarding 文档需**快照**分配结果（算一次、存 catalog + 分数），而非每次实时重算，避免"代码没动、文档却变"。
- ⚠️ **基础设施成本**：Embedding 需模型 + 向量索引；本地(sentence-transformers)重、API(轻但涉成本/隐私)——需定本地还是 API（见 §12.4）。

### 12.4 待定子决策（进入 M1 前需定）
- **Embedding 来源**：本地模型（sentence-transformers，离线/隐私好/重）vs API（轻/成本/隐私顾虑）vs 混合（本地小模型做主、API 兜底长文本）。
- **快照策略**：首次全量算一次存 catalog；增量时仅重算变更符号的向量与归属；阈值与质心随生命周期版本化。
- **检索入口（已定）**：暴露一个**语义查询封装（向量库 + 查询 API）**，而非仅固化进 catalog 只读。双主线并行、互不为主 → 检索层**不做事前融合**，把"向量侧结果 + 注释侧结果"**同时返回 Agent 由它自裁决**（见 §13.4）。

### 12.5 与 §9/§11 的关系
- 不推翻既有决策：MkDocs/mkdocstrings/llms.txt、功能域重归类、生命周期三段式、前端 A 为主 + B 补充 **全部保留**。
- 向量层是**叠加**在分类与渲染之上的"归因与检索引擎"，让"全库纳入 + 省 Token"的张力进一步缓解：未标注代码靠向量自动入域，无需人工逐文件贴标签。

### 12.6 归因裁决：显式键 ⇄ 向量 平等融合（用户定，互不为主）
最终"符号 ∈ 哪些域"由显式键与向量**平等融合裁决**，任一方都不先验占优：
- **仅键 或 仅向量 单方出现** → 该方结论即采纳（无冲突，单方说了算）。
- **键存在 且 向量 top 域一致** → 高置信，采纳（双方印证）。
- **键存在 但 向量 top 域不一致** → **不自动偏向任一方**，标 `conflict: true` 交人工裁决（键值可能标错、向量可能误判，二者同等可疑）。
- **键与向量双高置信且重叠** → 视为跨域软归属（多域分布），catalog 记分布而非强制单域。
- **双方皆弱 / 向量低于阈值** → 标 `uncertain` 进待复核队列。

> 说明：B/C（Storybook / Ladle-Dumi 的 demo 与可视化）属文本方向的**展示层**，**不参与归因裁决**；裁决只在「`@domain` 显式键」与「向量隐式轨」之间发生，且二者地位平等。此前的"键是真相源"表述已废止——改为平等融合、冲突交人，正是对用户原始向量设想（不先验抬高任一方）的回归。

### 12.7 两大方向最终形态（汇总，地位平等）
```
                 目标项目知识库（示例）
                        │
        ┌───────────────┴───────────────┐
        │     能力域 Domain（统一框架）    │
        │   ├─ 可读产出：TypeDoc(A)       │
        │   │            + Storybook(B)   │
        │   │            + Ladle/Dumi(C)  │
        │   └─ 归因/检索：向量方向        │
        └───────────────┬───────────────┘
                        │
        ┌───────────────┴───────────────┐
   方向一·文本注释层 ⇄ 方向二·向量智能层   （地位平等，互不为主）
   TypeDoc(A)主线+Storybook(B)+Ladle(C)  内部双轨（平等）：
   → 域 landing/模块页/API参考/demo       ├─ 显式轨：@domain 单一键
                                          └─ 隐式轨：Embedding 相似度
```

### 13.1 主线一 · 输入与源真相（已细化 · 余 1 待定子项）

**输入边界模型（已定 · 路线 C 混合）**
- 显式根目录（由 `config.yaml` 定义，示例：`agent/` `apps/` `gateway/` `wiki/` `reports/` 等语义独立的顶层源；**实际项目按自身结构配置，不硬编码**）+ 自动扫描子项 + 黑名单排除（`node_modules`、`__pycache__`、构建产物、自产 `docs/api/` 等，**同样走配置**）。
- **root 两种写法（实现补充 2026-11-15，用户复核）**：`- path: <dir>` 递归扫描（默认）；`- path: <dir>` + `files_only: true` **只扫该目录顶层文件、不递归**。用途：项目**根级核心代码**（`cli.py` / `hermes_state.py` / `run_agent.py` 这类大而关键的入口）往往不在任何子模块目录里，若因「文件大/怕拖入巨型子目录」整层排除，知识库就丢了主脉络——这是过度裁剪，不是合理取舍。`files_only` 让根级文件可单独纳入，同时不把同目录下的 114M 巨型子目录一并拖入。
- **大文件非拒绝理由**：实现层须避免 O(n·行数)/O(n²) 退化（`ast.get_source_segment` 整篇只切一次 + 一次建父映射，实测 846K `cli.py` 提取 2.58s→0.17s），而非把大文件排除出语料。详见 `<e2e-artifacts>/TEST_REPORT.md` §9。

**代码有效性甄别（valid/invalid triage）—— 用户新增机制**
- 目标：在文件级排除之外，进一步判"有效代码 vs 无效代码"（测试、示例、死代码、生成物等），避免文档被噪音稀释。
- **主路径 · 内置启发式（确定性，优先）**：默认走 **模板 / 文件名 / 扩展名 / 格式** 判别（路线 C 自动扫描方向）——如 `*.test.*` `*.spec.*` `__tests__/` 判测试，`*.generated.*` 判生成物。零人态下优先用确定性规则：省 AI 调用、可复现、不依赖模型可用性。
- **升级路径 · Agent 驱动（内置解决不了才用）**：当内置启发式**无法判定**（歧义 / 无规律 / 新形态）时，才退化为文档系统以 **Skill / MCP** 形态提供的接手 Agent 判定；Agent 判有效/无效并 **格式化输入回传**，文档系统据以标注。
  - 跨线：此形态与 **主线七（接入协议）** 重合——读用 Skill、写用 MCP（见 §13.7）；回传格式复用 catalog 结构（`file / validity / reason / suggested_domain`），直接落库。
  - 元架构：文档系统 **以 Skill/MCP 提供给 Agent** 本身即其实现方向（Agent 帮助哺育文档系统，呼应 §9 的 Agent 动态优化）。
- **标记可编辑**：validity / 域标签等标注层做成 **可修改、可版本化**，预留未来用途，不硬编码。

**与主线二衔接**：有效性甄别是归因（§12）的**前置过滤**——无效代码不进归因与渲染。

**封装形态（已由 主线七 §13.7 闭合）**：读 = Skill（给 Agent 读指南，零写能力），写 = MCP（git 式提交，`change_reason` + 幂等键 + 非只读签名）；二者共用、按读写分工。原「倾向 Skill」的判断被 §13.7 的「读 Skill / 写 MCP」取代。

**各语言/格式的提取策略（✅ 已定 · 方案乙 → 方案甲统一接口，内置优先 + AI 升级）**
- **流程（用户拍板）**：① 先甄别文件是否有效（见上，**内置启发式优先**）→ ② 对有效源**先靠内置识别方案**抽取 → ③ **按方案乙**写**各语言提取脚本**（起步不做抽象层，靠约定如源顶部 `@domain` 统一口径）→ ④ 脚本输出**转换成方案甲的统一接口**（中间表示 `Symbol[]`：每项 = 符号 + docstring + `@domain` + 签名），上游甄别 / 归因(§12) / 渲染(§13.3) / 三件套向量化只认这个统一接口 → ⑤ **若内置识别方案不能解决（歧义 / 无规律 / 新语言），升级为 AI 提取**（Agent 驱动，回传同构 `Symbol[]`）。
- **语言适配器清单（方案乙初始实现，内部细节，可增）**：
  - Python：`mkdocstrings` / `ast` → `Symbol[]`
  - TypeScript：`TypeDoc` / `ts-morph` → `Symbol[]`
  - wiki / reports：纯文本解析（标题层级 / 链接 / `@domain`）→ `Symbol[]`
  - 未来新语言：加一个适配器即可，**不动统一接口与下游**。
- **设计要点**：统一接口（方案甲）是**目标形态**、方案乙是**起步实现**——先低成本按语言分支写脚本，抽出结构归一化到 `Symbol[]`；只有内置脚本覆盖不到时才调 AI，避免把 AI 当默认抽取器（省成本、可复现、零人友好）。

**源真相中间产物（✅ 已由 主线三 Q4 闭合 + 用户补充 · catalog 快照 + 增量重算 + git 式版本化 + 漂移兜底）**
- **基础（Q4）**：取 **catalog 快照**（提取结果 `Symbol[]` 物化为持久 catalog，渲染/归因只读快照，不做「渲染时现提」）；靠 **Q1 增量重算（内容哈希，非 mtime）** 保持新鲜，只重算变更文件，避免「现提」全量重抽成本；校验门（§13.6）兜底禁发布失败/幻觉页。即「存快照、但用增量让它像现提一样鲜」。
- **git 式 catalog 版本化（用户补充）**：catalog 自身按 §13.5 / §13.8 Q-3 的 git 式范式管理——**每次重算产出 = 一次提交**，强制 `change_reason`，可回滚到任一历史提交；catalog 的 `active` 即「当前已发布版」，历史提交串成版本链。与 §13.8 Q-3 的「提交+原因+回滚」完全同构，只是对象从 KB 整体细化到 catalog 这一中间产物。
- **未提交代码改动的漂移兜底（用户补充 · 关键）**：源码工作区可能**领先于 catalog**（改了代码但还没触发重抽/提交 catalog），二者出现 **hash 漂移**。处理四原则：
  1. **读侧不破**：继续服务上一个**已提交** catalog（旧信息不消失、不幻觉），绝不因漂移返回空/错——呼应 §13.6 Q-B「读写侧分工」。
  2. **标脏不阻塞**：检出漂移即标 catalog 为 `behind`/脏，记录「工作区比 catalog 多 N 个文件改动」，交给下游触发，不卡读取。
  3. **自动对账**：由 **主线五 触发层**（git hook 提交时 / Agent 动态维护 / §13.8 U3 的 TTL 巡检兜底）自动重抽变更文件 → 生成新 catalog 提交（`change_reason` 如 `auto-reconcile: 工作区 N 文件漂移`）。**分层触发 + TTL 巡检存在的主因之一，就是兜「改动未及时提交」这种窗口。**
  4. **fail-closed 只卡"发布"不卡"读取"**：漂移期间若 CI 校验门判定 catalog 与源严重不符，禁发布新版本、降级到上一提交，但读取仍可用。

### 13.4 主线四 · 索引与检索（已闭合）

**两层检索模型（总览）**
- **表层（确定性索引）**：llms.txt / 每页 `.md` twin / 结构化 INDEX.json —— Agent 先拿小索引把握全库布局，再按需深入（见 §11/§13.3）。人类走 MkDocs 站内搜索。
- **深层（语义检索）**：主线二向量方向 —— Agent 用自然语言提问直接命中符号/模块，无需精确关键词。

**Agent 检索接口契约（已定 · 向量 + 注释 + 注释文本 三者全给，Agent 自裁决）** — 用户定：沿用主线二的同一套口径，每个符号侧携带三类信息——**向量**（Embedding 相似度/归属）、**注释**（`@domain` 显式键，人工信号）、**注释文本**（TypeDoc/docstring/可读 note，文本方向产物）。双主线并行、互不为主 → 检索层**不做事前融合**，而是把这三者**同时返回给 Agent，由 Agent 自己判断权重与冲突**。
- **读取 / 浏览路径**：返回每个符号的「向量结果 + 注释（@domain 键）+ 注释文本（可读页/docstring）」三者，Agent 自行综合。
- **查询路径（语义查询）**：抓向量的匹配结果（按相似度 top-k），并把每个命中项的「注释（@domain 键）+ 注释文本（可读 note）」一并返回。即每个候选都携带「向量相似度分 + 注释 + 注释文本」三者成对返回。
- **向量近邻返回（用户补记 · 怕忘，先归档）**：除三件套外，检索接口**还要返回向量空间中距离最近的前 N 个符号**（nearest neighbors，各带相似度分）。用途：让 Agent 看到"这个符号语义上挨着谁"，直接支撑 §12.3 的多域重归属 / 语义混淆 / 影响面判断。定位：属于 **"向量"维度内的扩展**（近邻列表），**不是第四类原始信息**，三件套口径不变；N 由 `config.yaml` 定（默认值待 M1）。读取 / 查询两路径都附加。
- **不预融合**：系统不在服务端做混合排序/裁决（呼应 §12.6 的"互不为主"）；权重、冲突、取舍全交给 Agent。
- **接口形态**：暴露一个语义查询封装（向量库 + 查询 API），而非仅固化进 catalog 只读（闭合 §12.4 检索入口子决策）。

**payload 草图（字段待 M1 敲定）**
```
result_item = {
  symbol,            # 符号/模块标识
  vector,            # 向量：Embedding 相似度分（查询路径有；浏览路径可为归属置信度）
  vector_neighbors,  # 向量近邻：距离最近的前 N 个符号 [{symbol, score}]（用户补记，见上）
  annotation,        # 注释：@domain 显式键（人工信号，来自 §11.8 / §12.2 显式轨）
  annotation_text,   # 注释文本：docstring / 可读 note / 页面摘要（文本方向产物）
  source_ref,        # 指向 MkDocs 页 / 源码位置
  conflict_flag      # 若显式键与向量结论冲突（来自 §12.6），提示 Agent
}
```

**仍待细化（主线四范围内）**

  - **先厘清「索引是什么方面的索引」（用户本轮追问）**：本项目里"索引"一词被四种含义共用，Q7 特指第一种。

    | 索引 | 索引对象（维度） | 回答什么 | 是不是原始信息 |
    |---|---|---|---|
    | **`llms.txt` / 分片（Q7 主角）** | **结构 / 位置 / token 成本 / 新鲜度** | 有什么、在哪、多贵、多新 | 否，派生导航指针 |

    | 全文 / 倒排（PageFind 等） | 词项 | 哪页提到 X | 否，派生词表 |

    **原始信息 = 源码 / docstring / `@domain` 键 / 注释文本**（及由其算出的向量坐标）。索引是从原始信息**派生出的指针**，只抽位置与元数据、不复制内容。所以 Q7 问的"索引和向量怎么衔接"，本质是 **"结构导航指针"与"语义坐标"这两份派生材料，怎么和原始信号一起交给 Agent**。
  - **我能想到的 + 世界上存在的方案（合并，优缺点给全）**：

    | 方案 | 做法 | 优点 | 缺点 |
    |---|---|---|---|

    | **C 自适应 / 分阶段（graduation / phase-based loading）** | 默认 A；任务明确（已知符号名）允许直跳向量查询 / 直读；探索性任务才先读索引 | 兼顾延迟与省 token；世界称 Retrieval Infrastructure Graduation（filesystem→semantic→graph 按需升级） | 需路由判断、编排更复杂；若路由做成系统硬编码，又退回 oversteering |
    | **D 三层化（index → summary → full）** | 把"两层"拆成三层：L1 索引 / L2 向量 top-k 轻量候选（摘要层）/ L3 命中项展开注释+注释文本（全文层） | 与 §13.4 payload **三件套天然对应**；世界三层共识（~50–100 → ~200–500 → ~500–1000 token/项），约 10x 省 token | 需多产一层轻量摘要；索引层太稀疏会选不准 |

### 13.5 主线五 · 生命周期与维护（✅ 闭环）

**定位与边界（先划清职责，避免与主线六打转）**
- 本主线 = **"一次变更从发生到生效"的时间轴主干**：让文档/索引与代码保持同步、可追溯、可回退。
- **与主线六分工**：主线五管「触发 / 同步 / 版本 / 新鲜度信号」；主线六管「质量达标判定 / 覆盖率 / SLA 是否达标 / 校验门判定规则」。校验门横跨二者——**门的存在与触发在五、判定规则在六**；新鲜度**信号**在五、新鲜度 **SLA 达标**在六（承接 Q7 移交项）。
- **保留** §9 三段式（首次全量 → 变更增量 → Agent 任务动态优化）、Q4（catalog 快照 + 内容哈希增量）、Q6 通用原则（所有增强走 `config.yaml` 开关）。

**七段式变更链路（主干）**：`T0 触发 → T1 变更检测 → T2 影响面 → T3 增量重算 → T4 校验门 → T5 原子发布 → T6 陈旧治理`，外加 `R 全量重算红线`。以下逐段给「推荐主路线 + 备选及优缺点 + 世界实践」。

> **术语注（用户追问后补，避免反复卡壳）**：**git** = 版本管理工具，`commit` = 把一次改动记进本地历史、`push` = 把改动传到远端仓库。**git hook（钩子）** = git 自带的机制，在 commit / push 等动作发生的瞬间，自动触发一个你放的脚本（放在 `.git/hooks/`）。我们借它做"提交时自动重算变更文档"。**CI（Continuous Integration，持续集成）** = 远端服务器上的自动化流水线，代码 push 上来后自动跑一整套"构建 → 校验 → 发布"，代表实现如 GitHub Actions / GitLab CI / Jenkins。**关键差别**：hook 在**你自己的电脑**上跑（快、但可 `--no-verify` 跳过、各人环境不一、管不到网页端改动）；CI 在**干净公共机器**上跑（可复现、谁都绕不过、有日志）。注意是 **CI**（字母 I），不是 CL。

**E1 · T0 触发分权（推荐：分层且分权，非三选一）**
- 三种触发：git hook（提交时）、CI（服务端权威）、Agent 动态（任务内）。**关键洞察：三者不是竞争而是分层**——Agent 动态刷新的本质是 **主线一「回写 catalog 标注」（validity / domain）**，是**标注、不是发布**；因此它不该绕过校验门。这样把主线一与主线五串成一条：Agent 哺育标注 → hook 快速增量 → CI 权威校验发布。
- **「分权」比「分层」更准（用户追问后采纳）**：分层讲高低/先后，但这里三者**不是排队关系，而是权限不同**。系统里真正的权力只有一种——**能否改写 `active`（对外真相、Agent 实际读到的那份）**。据此三层权限：
  - **Agent 动态 = 建议权**：只写 catalog 候选层的软标注（`validity` / `suggested_domain`），可编辑 / 可版本化 / 冲突交人；**不碰** MkDocs 页、llms 分片、向量质心，更不能碰 `active`。
  - **git hook = 预审权**：按内容哈希重算、写**本地候选副本**供即时预览；但可 `--no-verify` 跳过、各人环境不一、覆盖不到网页端/协作改动 → 其产物**不具备权威性**。
  - **CI = 唯一发布权**：唯一跑完整链路 + 校验门 + manifest，校验通过才原子切 `active`；可复现、可审计、可回退。
- **一个思想实验（为什么必须收口）**：若让 Agent 干活时顺手改写 MkDocs/llms.txt，等于把**概率性、可能带幻觉、不同 run 结果不同**的输出直接写进真相源 → 污染此后所有 Agent、无法复现、无校验门、无回退，正面违背 §12.3（快照确定性）、§12.6（冲突交人）、Q7（不预判）。但 Agent 又不能"什么都不写"——主线一已把它设计为**有效性甄别 + 格式化回传标注**的生产者、知识库的哺育者。于是给它**建议权**：产出进候选层，等 CI 收编。
- **与全稿哲学的对称（关键，化解表面矛盾）**：全稿一路定「原始信息尽量全给 Agent、不预判、不融合」——那是**读侧**；分权管的是**写侧**。**读侧放开放、写侧严收口**，二者作用在相反方向，并不矛盾：给 Agent 最大的读取自由度、只给它最小的写入权；"让它自己去想"指的是**裁决材料**，不是**改写真相**。
- **可迁移心智模型**：不是"三个触发源"，而是「**多个提议者 + 一个裁决者 + 一道闸门**」——谁都能提 PR（Agent/hook 写候选），但只有 CI 绿了才能 merge 进 `main`（`active`）。这也解释了 E5 为何必须先 `v_next` 后切换：提议再多，同时只有一个生效版本。
- 选项优缺点：
  - *仅 git hook*：✅ 快、零基础设施；❌ 可 `--no-verify` 跳过、各人环境不一、覆盖不到网页端/协作改动。
  - *仅 CI*：✅ 权威、可复现、集中；❌ 分钟级延迟、吃 CI 资源。
  - *hook + CI 双轨（推荐）*：✅ hook 快 + CI 兜底权威；❌ 两处逻辑须共用**同一个生成器入口**（否则漂移）→ 由主线七的 Skill/CLI 统一封装解决。
  - *watch / 定时轮询兜底*：✅ 覆盖漏网变更；❌ 常驻进程 / 成本 → 列为可选项、默认关。

**E2 · T1 变更检测（推荐：内容哈希 + 忽略区 + 文件级起步）**
- **内容哈希 SHA-256，非 mtime**——mtime 会被 checkout / 格式化工具误触发；世界实践：哈希比对减少 80–95% 重嵌入。
- **忽略区配置**：把页脚 / 修订日期 / 生成时间戳等"易变但无关"区域排除出指纹。世界实践踩坑：页脚加一行修订日期 → 整篇指纹变 → 误判大改、全量重切。示例映射：生成头、时间戳注释可配忽略（按目标项目配置）。
- **指纹粒度**：文件级（✅ 简单；❌ 改一行整页重算）vs 符号级 tree-sitter 真增量（✅ 细、省；❌ 重、需 AST 基建）。推荐**文件级起步 + 符号级押后**（Q4 已提 tree-sitter/libclang）。
- **身份字段别混**：世界实践强调「别把 content_hash 当 doc_id」→ 拆 `doc_id`（稳定主键）/ `source_version`（单调递增）/ `content_hash`（去重与缓存键）。

**E3 · T2/T3 影响面 + 增量重算**
- 依赖图**反查**受影响的域页 / 模块页 / llms 分片 / 向量条目 → 只重算这些；文本未变则从 `(content_hash, embedding_model)` **缓存复用**向量。
- 世界实践踩坑：影响面**只按"改了几个文件"算风险不够**，应「文档热度 × 变更幅度」，高频模块的小改也标红走人工复核 → 此复核动作**移交主线六**。
- ✅ 选择性重算省算力；❌ 依赖图要准，漏一条依赖就有陈旧页 → 靠校验门 + 新鲜度戳兜底。

**E4 · 快照身份升级（把 §12.4 catalog 快照做成版本指纹）**
- 字段：`doc_id / source_version / content_hash / index_version / embedding_model / chunker_version / thresholds_version / centroid_version` + 不可变快照 + manifest。新版本用独立 key，避免与旧版互相覆盖。
- ✅ 可追溯 / 可回退 / 防混合代；❌ 字段多、存储与维护成本（用户对"维护重"已定调可接受）。

**E5 · T4/T5 校验门 + 原子发布**
- 先在候选版本 `v_next` 构建，**校验通过才把 `active` 原子切到新版**；旧版后置清理、可重试（世界实践：v18 构建时用户仍读完整 v17）。
- **顺序红线：先写新 → 确认索引就绪 → 再回收旧**。世界实践踩坑：先删旧再写新，中间出现几秒"新旧都召回不到"的空窗 → 空答。
- 校验门内容（呼应 Q4）：构建失败 / 幻觉页 / 死链 → **禁发布、保留上一版**；manifest 校验（chunk 数量、模型版本）。**判定规则细节归主线六**。
- ✅ 无空窗、可秒级回退；❌ 短暂双版本存储。

**E6 · T6 新鲜度治理（信号层）**
- 每页/每条带时效元数据：`indexed_at / expires_at / content_hash / shelf_life / source_version`（世界实践）。
- **保鲜期分级**（按内容稳定度）：架构/域 landing ~1–2 年、API/模块页 ~2 周–1 月、变更日志 ~7 天；示例映射：域 landing 慢变、模块页随代码、llms 分片每次变更（按目标项目配置）。
- **过期指数** = 距上次更新 / 可接受周期，逼近上限自动列入「待审队列」（→ 主线六复核）；旧版**墓碑归档**、不两版并存。
- ✅ 把"文档腐化"从隐性变可监控数字；❌ 需为每类内容定 `shelf_life`（配置化，Q6）。

**E7 · R 全量重算红线（模型漂移）— 关键**
- **必须全量、禁止增量**的触发：首次；`embedding_model` / 分块逻辑 / 阈值 / 质心 / schema / `domains` 白名单变更。
- 世界实践强警告：增量/CDC **必须用与现有索引完全相同的预处理与模型版本**，否则产生「混合代向量库」，几何不一致**比不更新更糟**。
- 由此闭合 §12.3「相似度随模型漂移」风险 与 §12.4「阈值与质心随生命周期版本化」；定期全量兜底列为可选（修复未检测到的漂移）。

**E8 · 一致性与顺序（轻量起步）**
- 幂等 + CAS：允许事件重复处理，以条件更新发布版本；配合「先写新后回收旧」。
- 世界实践的 Outbox / Kafka / Debezium 是超大规模（5000 万向量、日均 300 更新）方案；**单机文档系统不需要**，列为「规模升级时再引入」，避免投机式基础设施（呼应核心窄腰原则）。

**主线五小结 + 相邻接口**：把 §9 三段式从口号落成「**七段链路 + 全量重算红线 + 快照版本指纹**」。入自 主线一（有效性甄别 + 快照）、主线二（向量/质心）、主线四（Q7 移交：索引持续更新、缓存按哈希失效）；出向 主线六（校验规则 / 复核队列 / SLA 达标）、主线七（统一触发入口 = Skill/CLI）。

**✅ 一处与世界实践冲突（已定 · 用户认可裁决）**：世界实践主张「对陈旧片段**降权 / 拦截召回**、答案强制引用版本」；但全稿哲学是「**原始信息尽量全给 Agent、不预判、不融合、交 Agent 裁决**」（§12.6 / §13.4 / Q7）。二者正面冲突。**用户认可裁决：系统只打时效标 + 墓碑，不拦截、不降权，让 Agent 自己看见新鲜度并判断**（与全稿一致）；世界做法作为「人类团队介入时的可选严格模式」，`config.yaml` 开关、默认关。

**主线五拍板进度**：① 触发分层 —— 用户认可，另要求讲解"分权"，已补于 E1（本轮）；② 指纹粒度文件级起步、符号级押后 —— 随主路线认可；③ 冲突裁决 —— 用户明确认可「只打标不拦截」✅。**主线五 3 点已全部闭合** → 进 **主线六 · 质量与治理（§13.6）**。
### 13.6 主线六 · 质量与治理（✅ 闭环）

**定位与边界（承接 §13.5）**：主线五管「触发 / 同步 / 版本 / 新鲜度**信号**」；本主线管「**质量是否达标的判定 / 覆盖率 / SLA 达标 / 校验门判定规则 / 复核队列消化**」。校验门横跨二者：五管"门的存在与触发"，六管"门里判什么、门槛多少"。

#### 13.6.1 两轮网查的合并结论（先说最刺骨的一条）
- **世界实践一致默认末端有"人工审查"兜底真值**。Docs-as-Code 的 CI 四层门禁（① 断链 lychee/HTMLProofer ② 风格 Vale+markdownlint ③ 新鲜度 `last_reviewed`+tier 超窗即失败 ④ 代码-文档联动 Danger 规则）**只验证文本属性，不验证句子是否为真**——军舰日志那篇的原话：「一个流畅但描述已删除服务的页面，四条全过」；Document Quality Assurance 也说语义审计 7 问里「功能是否真存在 / 声明是否仍成立 / 有无矛盾 / 版本 / 示例能否跑」**需要人工判断**，只有断链和计数可自动化。Heyzeva 三层、CRP、GroundCheck 遇到无支撑证据时一律 `hold flag → 暂停交人工`。
- **而我们的零人定调恰恰抽掉了这一环** → 主线六真正要解的题不是"加哪些 lint"，而是 **「零人时谁来做真值审查」**。
- **另一条反向印证（很漂亮）**：GroundCheck 在证据冲突时输出 `conflicted_evidence` verdict 并**把两段引用并排呈现**、低于阈值就**诚实弃答（abstention）**而非编造——这与全稿「冲突两侧原样并列交 Agent 裁决」（§12.6 / §13.4）+「fail-closed 不裁决」（§14.5）**完全同构**。世界实践再次从侧面印证了我们的哲学。

#### 13.6.2 质量维度与零人 KPI（把 §1 验收标准操作化）
| 维度 | 世界可操作指标（可直接借） | 零人态落地 |
|---|---|---|
| **准确性 / 真值** | Citation coverage ≥95%、Verification pass rate ≥90%、claim groundedness、citation precision/recall、fabrication/distortion 检出数 | 声明级溯源 + NLI 蕴含判定（见 13.6.3）；**不可核验 → `unresolved` 冻结，不编造** |
| **新鲜度** | Freshness SLA 分档滞后（P0 ≤4h / P1 ≤24h / P2 ≤72h）；`last_reviewed`+tier 超窗即失败 | 承接 §13.5 E6 的时效元数据与过期指数；**只打标不拦截召回**（§14.7 已裁决） |
| **覆盖率** | 符号/模块级（非全库体积）、OpenAPI/Swagger coverage、canonical doc 缺失即 block merge | 按 §11 的 域/模块两级 度量；**按效用不按体积**（documentation-auditor 反模式） |
| **可发现性** | Search success rate ≥70%（周评测集"找到+有引用+版本正确"） | Agent 侧用 §13.4 接口做**轮换监控查询**；人读侧用站内搜索 |
| **一致性 / 溯源** | 每页绑定 commit（防 Franken-docs 混合版本）、每技术声明链到源+锚点、版本完整性 | 呼应 E4 快照版本指纹；**真值源优先级**见 13.6.5 |
| **加权总分** | documentation-auditor：accuracy 30% / freshness 25% / coverage 25% / discoverability 20% | 可作仪表盘总分，但**不代替硬门禁**（分数会互相掩盖） |

#### 13.6.3 核心决策 Q-A：零人时"真值审查"由谁做（给选项 + 优缺点）
| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 只做四层文本门禁** | 断链 / lint / 新鲜度 / 代码-文档联动 | 最轻、纯确定性、零 LLM 成本、实现快 | **抓不住幽灵功能与虚假声明**（P0 语义错误全过）；世界明确说这只验证文本属性 |
| **B 声明级溯源 + 自动事实核查（★ 推荐核心）** | 把生成页拆成原子声明 → 只挑 FACTUAL_CLAIM → 检索源码/docstring 作证据 → NLI 判 entailment/contradiction/neutral → 加 attribution 分数与 distortion 六型检测（数字改写 / 否定翻转 / 限定词增删 / 范围扩大 / 实体替换 / 语义漂移）→ 无支撑则 `unresolved` | 把"人工语义审查"自动化，且**零人态可闭环**；CRP 13 模块、自动事实核查三阶段、GroundCheck 都是成熟路径；与全稿"溯源优先"一致 | 最重；每条声明 200–500ms；NLI 自身会误判 → 需多模型交叉 + fail-closed；误报可能卡住发布 |
| **C 结构化输出校验** | 比对"已验证草稿 vs 发布态"的 delta，格式化/模板注入引入的新错误触发 re-review | 堵住 Heyzeva 指出的"验证后又被改坏"隐形失效；纯 diff、确定性、便宜 | 只管"没被改坏"，不管"原本对不对" → 必须与 B 叠加 |
| **D 只让生成侧自检** | 让写文档的 AI 自己检查自己 | 零额外基建 | **Degeneration of Thought**（§14.3c）+ 违反**结构性不自审** → **排除** |
| **E 留人审末端** | hold flag 交人 | 世界标准做法、真值最可靠 | **零人态直接不能运行** → **排除** |

**推荐主路线：B + C + A 三层叠加**（声明级真值 → 发布态完整性 → 文本门禁），**D/E 排除**。判定不确定的一律走 §14.5 的 fail-closed，不猜。

#### 13.6.4 核心决策 Q-B：门禁判定规则与"只打标不拦截"会不会打架
- **不打架，因为作用在不同侧**（延续 §13.5 那个"读侧放开放 / 写侧严收口"的对称）：
  - **读侧 / 召回侧**：陈旧内容**只打时效标 + 墓碑，不降权、不拦截**，全给 Agent 自判断（§14.7 已裁决）。
  - **写侧 / 发布侧**：新 `v_next` 若未过硬门禁（P0 声明不可核验、断链、缺 canonical 页），**禁发布、保留上一版 `active`**（§13.5 E5 已定）。
  - 一句话：**"不让旧信息消失" ≠ "让不合格的新版本上岗"**。
- 门禁规则本身属于**宪法可修订层**（阈值、分档、白名单）→ 修改走 §14.5 typed amendment + 异构审核群，防止 AI 悄悄放宽质量门槛（这正是 Ouroboros 式自我放宽的高发区）。

#### 13.6.5 核心决策 Q-C：真值源优先级（零人时"以什么为准"）
世界实践（j77.ai）给的是**优先级层次**，不是平级投票；Heyzeva 还明确**排除 AI 生成内容作为 grounding 源**（防"AI 摘要引 AI 摘要"的循环引用）。据此给三个选项：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **S1 源码唯一论（★ 推荐）** | 真值源 = 源码 / docstring / 已验证配置 + git 历史；**文档与 catalog 都属派生，不得反过来当证据** | 彻底切断循环引用；与主线一「源真相」、§3「溯源优先」一致；确定性最强 | wiki/reports/AGENTS.md 这类"约定性文档"的真实意图无从源码验证 → 需另设通道 |
| **S2 分层优先（世界主流）** | spec/schema > 已发布代码 > 配置 > runbook > ticket/ADR；冲突时按层级裁决并显式标注 | 覆盖真实项目的多源现实；冲突有明确规则 | 需要人工维护优先级与 owner 映射（零人态要改为 config 声明 + AI 维护） |
| **S3 平级投票** | 各源平等，多数者为准 | 简单 | 派生文档与源码同权 → **循环引用风险**；与全稿"溯源优先"冲突 → 排除 |

**推荐 S1 为内核 + S2 为扩展**：代码类事实以 S1 为准；约定/意图类事实走 S2 分层，且**优先级表写进宪法可修订层**，由 AI 维护、变更走审核群。

#### 13.6.6 复核队列消化（承接 §14.6 #9）
`conflict` / `uncertain` / 不可核验声明 → 默认 **AI 消化**（异构 jury，§14.5）；判不了 → `unresolved` 冻结（§14.7 U3 唤醒）；冲突两侧**原样并排**交裁决席位（呼应 GroundCheck 的 `conflicted_evidence`）。**人层开启时只看升级项**，仍不做日常裁决。

#### 13.6.7 ✅ 已定案（用户「可以」，主线六闭合）
1. **Q-A = B + C + A 三层叠加**（声明级真值 → 发布态完整性 → 文本门禁），**D/E 排除**。
2. **Q-B 认可**：读侧不拦截 / 写侧严门禁；门禁阈值归**宪法可修订层**，防 AI 悄悄放宽质量门槛。
3. **Q-C = S1 源码唯一论为内核 + S2 分层优先为扩展**；**S3 排除**。
4. **追加裁决（用户认可）**：源码与 docstring/注释矛盾时，**判为「冲突并排」而非「不可核验」**，源码与注释两侧原样交给 Agent，不自动偏向任一方（见 13.6.8）。
> 全部 M1 待定：各阈值具体值、声明拆分/NLI 模型选型、轮换监控查询集、覆盖率口径 → 走 `config.yaml`。

#### 13.6.8 「源码唯一论」vs「源码/注释并排」为什么不打架（关键边界，防实现踩坑）
表面上 Q-C 说"以源码为真值源、派生文档不得当证据"，13.6.7 又说"源码与注释矛盾要并排"，似乎冲突。**实则是两个不同问题，各自落在不同侧**：

| | **真值判定（写侧 / 门禁）** | **材料呈现（读侧 / 检索）** |
|---|---|---|
| 问的是 | "这句声明**能不能算作真**" | "Agent 该**看到哪些材料**" |
| 规则 | **S1**：只有源码 / 已验证配置 / git 历史可作 grounding 证据 | **全给**：源码 + 注释 + docstring + `@domain` 键 + 向量 + 近邻，原样并排（§13.4 三件套本就如此） |
| 排除的是 | **派生 KB 产物**（生成的 MkDocs 页、catalog 快照、AI 摘要）反指自己 → 循环引用 | 不排除任何一手材料 |
| 对"注释"的定性 | 注释是**意图声明**，不能用来证明"功能已实现"（否则幽灵功能过关） | 注释是**一手原始信息**（§0.4 定义：原始信息 = 源码 / docstring / `@domain` / 注释文本），不是派生文档 |

- **所以不打架**：被 S1 挡掉的是「**生成的文档页 / catalog**」这类派生品；被并排的是「**docstring / @domain**」这类源码侧一手材料。两者根本不在同一个集合里。
- **判为"冲突并排"而非"不可核验"的理由**：`unresolved` 意味着"证据不足、判不了"，但这里**证据充分**——只是两个一手源互相矛盾（典型是注释没跟上重构）。这个矛盾本身是**高价值信号**（提示注释腐化），若折叠成"不可核验"反而把信息抹掉了，违反全稿「原始信息尽量全给 Agent、不预判」。
- **与全稿三处同构**：§12.6 归因冲突「不自动偏向任一方、交裁决席位」；§13.4 检索「三件套并列全给 Agent」；§13.5「读侧放开放 / 写侧严收口」的对称。GroundCheck 的 `conflicted_evidence` 并排呈现也是同一做法。
- **命名（M1 定）**：建议新增标记 `impl_intent_divergence`（实现-意图背离），与既有 `conflict`（显式键 ⇄ 向量）、`uncertain` 区分开；只作**标记 + 并排展示**，不触发拦截、不自动改注释。

### 13.7 主线七 · 接入协议（✅ 闭环 · 用户本轮拍板）

> 本主线回答设计稿最原本的那个问题：**一个对目标项目一无所知的新 Agent，具体怎么接手？** 把前面所有决策（Skill/MCP 形态、统一触发入口、零人自触发、只读 vs 回写分通道）收口成可执行协议。

#### 13.7.1 与既有决策的对接（不重复立论）
- §9 已定「**Skill + README 双写**」；主线一（§13.1）已定「文档系统**先以 Skill/MCP 提供给 Agent**，Agent 判代码有效性并**格式化回传标注**」，待决子项「Skill 还是 MCP」明确**指向本主线**。
- §13.5 E1 触发分权：Agent 只有**建议权**（写 catalog 候选层），**不能碰 `active`**；§14.6 #11 已定「定时 / 事件 / Agent 自身」可自触发，无需人发起。
- §14.7 已定**宪法起点 = AI 自举（从 AGENTS.md 抽取）**——本主线的接入入口与宪法来源是**同一份文件**，见 13.7.2。

#### 13.7.2 两轮网查的合并结论
- **AGENTS.md / Skills / MCP 是互补的三层栈，不是三选一**（agents.md 官方、CIOAge、dropagentic、arXiv 2611.03066 一致）：
  - **AGENTS.md** = 项目级契约，会话开始**自动注入**，无传输层、无协议；管"在这个项目里怎么做"（栈 / 命令 / do-not-touch / 约定）。官方建议**短（~50 行）**，因为每段都在每次请求付费；支持**嵌套**（子目录就近覆盖，OpenAI 主仓有 88 个）。
  - **Skills** = 任务级**程序性**知识，YAML frontmatter + `SKILL.md`，**按需加载**（progressive disclosure）；空闲约 ~100 tokens/个，10 个 skill ≈ 1 个工具定义。
  - **MCP** = 工具级**运行时连接**，Client→Server JSON-RPC；只在"要碰 live system / 你不拥有的状态"时才需要；工具定义**从第一回合就全额计费**，工具数一多就该改形状（code execution / deferred loading）。
  - 经验法则：**每个 session 都需要 → AGENTS.md；仅部分任务 → Skill；需要 live data → MCP**。业界预测是「MCP 做传输、Skills 做内容格式、AGENTS.md 做项目基线」。
- **⚠️ 提示词缓存与工具税**（呼应 AGENTS.md 项目核心原则）：核心工具每次 API 调用都发送，故 MCP 工具数必须克制；这直接支持"能力放边缘、不扩核心"的窄腰原则。
- **安全边界（必须记）**：MCP 规范自述「工具代表任意代码执行」「工具描述应视为**不可信**，除非来自受信任服务器」；Skills 同样是「指令 + 可执行代码」，尤其**从外部 URL 取数据的 skill 风险高**；progressive disclosure 的代价是「**你可能永远没读过那个最终会执行的文件**」。→ 本设计的接入层必须**审计未自写的 skill/MCP**、并把工具描述当不可信输入（与 §14 结构性不自审、§13.6 真值源同一警惕）。
- **★ 直接印证上一轮的反问**：最小权限实践一致要求「**只读与写入通道硬分离**」——"把权限写进工具签名，而不是写进提示词"（工具签名 `read-only` 是硬约束、提示词里的"不要写"是软请求）；"**Pair every write with a read**"（没有读就写 = 凭猜测改错对象）；"**分离 read / write 凭证**"；"**把模型提出的动作当不可信请求，由确定性执行器在执行前重新鉴权**"（plan is not permission，堵 TOCTOU）；"**Agent 不能写自己的审计日志**"（外部 append-only sink）。上一轮末我问「是不是该只暴露只读接口、把回写标注做成独立通道」——世界实践给的答案是**是，而且这是硬要求不是偏好**。
- **首次接手（onboarding）实践**：AGENTS.md 作为可预测入口 + 嵌套就近覆盖 + README 给人、AGENTS.md 给 Agent 的**双轨分离**；首次运行应**幂等**（重复接手不产生重复副作用）；能力发现用轻量元数据（Agent Card / skill description）而非全量工具列表。

#### 13.7.3 决策 Q-1：接入形态（给选项 + 优缺点）
| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **P1 纯 Skill** | 只做 Skill + README | 最轻、贴合通用 Agent skill 体系、零传输层、Agent 原生调用 | 无法暴露语义查询封装（§13.4 已定要暴露）；跨客户端/远程 Agent 不通用；能力发现弱 |
| **P2 纯 MCP** | 全走 MCP server | 跨客户端标准、live 查询天然、能力可发现 | 工具定义每回合计费（违窄腰）；需 JSON-RPC 基建；**入口不再只是"读个文件"**，零人自举变重 |
| **P3 AGENTS.md + Skill（★ 推荐内核）** | AGENTS.md 作**唯一入口/项目契约**，Skill 作按需程序（"如何接手""如何回写标注""如何触发维护"）；MCP 不进必需集 | 入口极轻（读一个文件）、与 §14.7「宪法从 AGENTS.md 自举」**同源**；零传输层；贴合窄腰；幂等自触发容易 | 语义查询仍需另给调用方式（文件/CLI 读 catalog 快照即可，不必 RPC） |
| **P4 三层全栈** | AGENTS.md + Skill + MCP（可选，config 开启） | 覆盖远程/live 场景、面向未来 | 多一套基建与维护；MCP 工具税；默认关时等于 P3 |

**✅ 已定案（用户拍板：「Skill 与 MCP 共用，按读写分工」）**：Skill 与 MCP 不是二选一，而是**按职责互补、各管一端**——
- **读 = Skill（读指南 / R 通道）**：Skill 作为按需加载（progressive disclosure）的程序性「读指南」，只告诉 Agent *怎么读 KB*（三件套 / 分片 llms / 向量近邻 / 索引路由），**本身不含任何写能力**；空闲约 ~100 tokens/个、零传输层，与 §13.4「读侧全给 Agent」天然契合——Skill 是说明书，不碰 live state。
- **写 = MCP（提交 / W 通道）**：所有 git 式程序化写入（回写 catalog 候选层软标注、带 `change_reason` 提交、CAS 回滚、版本切 `active`）一律走 MCP server，工具签名标非只读 + 字段白名单 + 幂等键。这正是 §13.8 Q-3 立下的「git 式版本化」**机制载体**——**W 通道 = git 式提交通道**，两条主线在此并轨。
- 由此主线一悬着的「Skill vs MCP」子决策**彻底闭合**：不是选哪个，而是**读靠 Skill、写靠 MCP**；AGENTS.md 仍是唯一入口 / 与 §14.7 宪法自举同源。MCP 不再「默认关」——它是写通道的必需基建；但具体暴露哪些写工具、工具数上限仍走 `config.yaml`（呼应窄腰与 §13.7.2 工具税）。

#### 13.7.4 决策 Q-2：只读 / 回写分通道（★ 本主线最关键）
| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **C1 单通道混合** | 一个 Skill/MCP 既能查也能写标注 | 实现最简 | **建议权与发布权在同一签名里**，一旦提示词被注入就可能越权写 `active`；违 §13.5 E1 分权；世界实践一致反对（软约束） |
| **C2 双通道硬分离（★ 推荐）** | 通道 R（只读）：查三件套 / 索引 / 语义检索，工具签名标 `read-only`；通道 W（回写）：**只写 catalog 候选层的软标注**（validity / suggested_domain / reason），不能碰 MkDocs 页 / llms 分片 / 质心 / `active` | 权限**写进签名**成硬约束；与 §13.5 建议权/发布权分权、§14 结构性不自审完全同构；注入攻击也越不过边界 | 两套接口要维护；W 通道需幂等键 + 字段白名单 |
| **C3 三通道** | R 只读 / W 候选回写 / A 审计日志独立 | 审计日志外部 append-only，Agent 写不到自己的日志（世界实践硬要求） | 多一套；A 通道可由非 Agent 进程承担而不必做成 Agent 接口 |

**✅ 已定案（用户拍板，与 Q-1 同批）**：C2 双通道硬分离落地为**读 = Skill / 写 = MCP**的硬分工——
- R 通道 = Skill（只读指南，签名 `read-only`，Agent 只能读、不能写）；
- W 通道 = MCP（提交，签名非只读，只能写 catalog 候选层软标注，越不过 `active`）；
- 审计日志仍由 §14.5 非 Agent 外部探针写入 append-only sink，**不做成 Agent 接口**（堵「Agent 写自己日志」）。
这与 §13.5 E1 建议权/发布权分权、§14 结构性不自审**完全同构**：Agent 的「建议权」物理上只能经由 MCP 写候选层，提示词注入也越不过工具签名边界；且因 W = git 式提交，每次写都带 `change_reason` + 可回滚（呼应 §13.8 Q-3），既是分权也是审计线索。「pair every write with a read」（写标注前必须先读当前 catalog 项）由 W 通道工具签名强制。M1 待定项相应收敛：Skill 只读指南清单 + MCP 写工具白名单 + 幂等键格式 + 工具数上限 → `config.yaml`。
> 这条同时闭合 §13.5 E1 里留的口子：**Agent 的"建议权"从此有物理边界，不再只是文档上的约定**。

#### 13.7.5 首次接手协议（零人态，幂等）
```
新 Agent 进入仓库
 → ① 读根 AGENTS.md（唯一入口，含 KB 位置、宪法指针、通道说明）
 → ② 读 llms.txt 根路由（§13.4 Q5 分片，带 token 成本）
 → ③ 按需拉域分片 / 三件套 / 向量近邻（§13.4 接口，读侧全给）
 → ④ 需要程序性步骤时加载对应 **Skill（读指南 / R 通道）**——如何读三件套 / 分片 / 向量；progressive disclosure，不含写能力
 → ⑤ 干活中判有效/无效代码 → 走 **MCP（W 通道）git 式提交** catalog 候选层软标注（带 change_reason + 幂等键）
 → ⑥ 事件/定时/Agent 自身触发维护（§14.6 #11）→ CI 校验门 → 原子切 active
```
- **幂等**：重复执行 ①~⑤ 不产生重复标注（靠 `idempotency_key` + 内容哈希）；⑥ 由 §13.5 E8 的 CAS 保证。
- **嵌套覆盖**：子目录可放自己的 `AGENTS.md`，就近优先（agents.md 官方约定），适配 1439 文件级的分域。
- **零人自触发**：全流程无需人发起；人层开启时只在 §14.5 的升级闸门出现。

#### 13.7.6 ✅ 已定案（用户本轮拍板，主线七闭合）

2. **Q-2 只读回写分通道** → **C2（读 = Skill / 写 = MCP 硬分离 + 审计外部化）**，与 §13.5 E1 分权、§14 不自审同构；**W 通道即 §13.8 Q-3 的 git 式提交通道**，两条主线并轨。
> M1 收敛：Skill 只读指南清单与 frontmatter 规范、MCP 写工具白名单 + 幂等键格式 + 工具数上限 → `config.yaml`。

### 13.8 主线八 · 度量与验收（✅ 闭环 · 用户本轮拍板）

> 本主线回答：零人定调下，**谁来看报表、谁来判定"系统达标"、怎么证明"新 Agent 真的更快接手了"**——而不是"文档生成了没有"。验收判据是「没有任何人类参与时，度量仍能闭环」，不是「有人读仪表盘时更好看」。与 §1 验收标准、§13.6.2 零人 KPI、§14.5 外部探针三者对齐，不重复立论。

#### 13.8.1 与既有决策的对接（不重复立论）
- §1 已列「成功标准」（准确性 / 新鲜度 / 覆盖率 / 可发现性 / 一致性）；§13.6.2 已把它们操作化成零人 KPI（citation coverage≥95%、Freshness SLA 分档、Search success≥70% 等）。本主线不重列指标，只解决**"这些指标在零人下怎么采、怎么判、谁执行"**。
- §14.5 已定「非 Agent 外部健康探针」管健康·新鲜度·指标真实性；本主线的**硬门禁由同一探针承担**，避免再引入一个"看报表的人"。
- §13.6 已定「加权总分只作仪表盘、不代替硬门禁」——本主线把这条钉成**正式的两类度量分工**（见 13.8.4）。
- §13.7 Q-2 已定「只读/回写双通道硬分离」——度量采集走 R 通道（只读），验收裁决走外部探针 + §14 审核群，**不再给 Agent 自评分的权限**（防"AI 给自己的文档打高分"，呼应 §14 结构性不自审）。

#### 13.8.2 两轮网查的合并结论
- **文档质量的终极判据是"功能效用"，不是"像不像人写"**（DocGenBench, 2026）：传统 BLEU/ROUGE 与功能性**相关性 <0.12**（lexical gap）；正确做法是"一个独立 LLM 仅凭生成文档能否重建代码并通过单测"（functional utility / pass@k）。**这直接印证全稿哲学：文档是 Agent 间的通信信道，不是给人看的工艺品**；也印证 §13.6 S1 源码唯一论——别用"AI 摘要像不像人写"评 AI 摘要。
- **仓库级文档评测应走"文档驱动开发"闭环**（SWD-Bench, 2026）：把 LLM 当仓库开发者，用"功能是否存在于文档 / 能否定位 / 能否补全实现"三类 QA + 真实改 bug 任务度量；最好的文档生成法让 SWE-Agent 解题率 **+20%**。**这就是"闭环验收"的范式：看 KB 是否真让 Agent 把活干成，而非看文档漂不漂亮。**
- **文档质量可拆成三层、各用最便宜的手段**（DocAgent, arXiv 2504.08725）：① Completeness = 确定性 AST/正则检查（结构是否齐）；② Truthfulness = 抽实体↔依赖图/真相源交叉验证（**与我们 §12 向量/catalog/依赖图同源**）；③ Helpfulness = LLM-as-judge 带 rubric+CoT+few-shot（主观维度才用 judge，且明确"不用于事实核查"）。→ 与 §13.6 的 A 四层文本门禁 + B 声明级溯源 + C 发布态校验 完全同构。
- **自主 Agent 系统的可观测性范式**（deployed.cloud / tsecurity / inferensys / surfs.dev 一致）：① 定义 agent-specific SLI（action success / permission violation / decision latency）+ SLO + error budget；② **行为金丝雀**（新版本小流量，对比基线 SLI，偏离即自动回滚）；③ **混沌演练**（故意杀连接/注入坏变更/模拟重复写，验证回滚与 ledger 防重）；④ **探针持续自证身份与环境**（"我是谁/环境还在吗"probe，呼应 §14.5）；⑤ **安全/审计日志与行为指标分离**（append-only，Agent 写不到）。⑥ 口号："boring to operate，只报 budget 与 drift，不报每条日志"。

#### 13.8.3 决策 Q-1：验收主体（零人下"谁判定系统达标"）
| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A1 外部探针自动门禁（★ 推荐·量化指标）** | §14.5 探针采集 SLI→比对 SLO→error budget 耗尽即自动降级/回滚/标 unresolved，全程无 Agent、无人类参与 | 零人成立、客观、可复现、fail-closed 兜底；与全稿"读侧开放/写侧收口"同构 | 只覆盖可量化硬指标；定性维度（helpfulness）需配合 A2 |
| **A2 异构 jury 验收（★ 推荐·定性维度）** | 复用 §14 审核群，对"helpfulness/可读性/是否真帮到接手"做裁决，dissent 强制可见 | 处理 A1 管不了的语义维度；复用既有基建不新增 | 耗算力、需异构防回音室（§14.3c） |
| **A3 Agent 自评分** | 让生成文档的 Agent 自己给质量打分 | 零成本 | **严禁**：自审=Degeneration of Thought（§14.3c），且违 §13.6 S1；等于让被告当法官 |

**推荐 A1 + A2 分工**：A1 管一切可量化硬指标（源真相/新鲜度/门禁通过率/fail-closed 兜底）自动裁决；A2 管主观维度（helpfulness）复用 jury；**A3 排除**。验收结论落 append-only 日志，由探针写，不是 Agent 写。

**✅ 已定案（用户拍板：「多 AI 审查 + 多 AI 自举 闭合 Q-1」）**：采纳 A1 + A2 分工、排除 A3。其中「多 AI 自举」复用 §14.7 的宪法自举基建——宪法核心、审核群、验收裁决共用同一套异构多 AI 流水线：零人态从 AGENTS.md 自举出第一版核心后，后续每次验收（含 helpfulness 定性）都由异构 jury 出裁决、dissent 强制可见。验收结论落 append-only 日志，由探针写、非 Agent 写。

#### 13.8.4 决策 Q-2：度量分两类（仪表盘 vs 硬门禁）
| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **B1 单类（全当门禁）** | 所有指标不达标就卡发布 | 最严 | 轻微漂移（覆盖率波动）就卡死发布，僵；与 §13.5"读侧开放"哲学冲突 |
| **B2 双类分工（★ 推荐）** | **硬门禁 SLO**=源真相/新鲜度/门禁通过率/fail-closed 兜底（blocking，违则禁发布/降级）；**仪表盘 informational**=覆盖率/可发现性/helpfulness 加权分（只报警、不卡发布，进 dashboard+KPI） | 关键维度铁腕、噪声维度不误伤；与 §13.6.2"加权总分只作仪表盘"一致 | 要分清楚每指标归属哪类（写 config.yaml） |
| **B3 全仪表盘（无门禁）** | 只采集不拦截 | 最松 | 零人下无人看报表=形同虚设，无 fail-closed 兜底 |

**推荐 B2**：硬门禁守"truth/freshness/gate"，仪表盘看"coverage/discoverability/helpfulness"。**"不让旧信息消失 ≠ 让不合格新版本上岗"**（§13.6 Q-B）在此落地为"硬门禁只拦发布、不拦读取"。

**✅ 已定案（用户拍板：「硬门禁用多 AI（即 Q-1 的 machinery），仪表盘就一个 AI）」**：采纳 B2 双类分工，并明确切分——**硬门禁（truth/freshness/gate，blocking）由 Q-1 的多 AI 担负**（A1 探针量化 + A2 异构 jury 定性），因为它直接决定"是否上岗"，必须多 AI 防自偏好；**仪表盘 informational（coverage/discoverability/helpfulness 加权分，只报警不卡）由单一 AI 产出**，因为它不阻塞发布、仅作观察信号，单 AI 可接受且省算力。每指标归属（门禁 or 仪表盘）写 `config.yaml`。

#### 13.8.5 决策 Q-3：闭环验收（怎么证明"新 Agent 真的更快接手"）
| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **C1 结构/文本指标代理** | completeness(确定性)+truthfulness(交叉验证)+helpfulness(LLM judge) | 便宜、日常可跑 | **只说"文档看起来好"，不说"真的有用"**；lexical gap 警示不能当效用代理 |
| **C2 合成接手基准（★ 推荐·发布前验收）** | 放一个独立"消费者 Agent"，**只给 KB、不给源码**，做一组预定义接手任务（定位功能/改已知 bug/加小特性/回答影响面），看成功率 / pass@k；KB 版本间对比 | 直接度量"Agent 接手效能"，是全稿哲学（文档=Agent 通信信道）的**终极验收**；离线、可回归、呼应 DocGenBench functional utility + SWD-Bench doc-driven dev | 需维护任务集与单测（§13.6.2 已定"轮换查询集"同源）；消费者 Agent 不能是生产者同模型（防自偏好，§14.3c） |
| **C3 行为金丝雀（★ 推荐·发布后守护）** | 新 KB 版本先小流量（仅某批 Agent session），对比基线 SLI（task success / search success / fallback rate / citation groundedness），偏离基线即自动回滚 | 在线守护、捕获 C2 离线漏掉的回归；呼应 agentic canary | 需流量分流与基线管理；长尾场景覆盖慢 |

**✅ 已定案（用户拍板：「做成 git 那样——首次建树与每次后期修改都提交、必须说明原因、且可回滚」）**：以 git 式版本化验收为骨架，再叠加 C2/C3 验证。
- **git 式提交模型**：① 首次全量建树 = 初始提交；② 后续每次增量维护/改动 = 一次提交；③ **每次提交强制附 `change_reason`（变更原因）字段**，无原因不准合入（呼应"说明原因"）；④ **随时可回滚**——任一历史提交可重新置为 `active`。
- **落到既有机制**：提交 = §13.5 的 `v_next` 构建 + 版本指纹（embedding_model/chunker/thresholds/centroid + manifest，E4）；合入 = T5 原子切 `active`（先写新→就绪→再回收旧，E5，避免空窗）；回滚 = 重新原子切回旧 `active`（CAS 保证，E8）；强制 reason = 在 manifest 增 `change_reason` 必填字段。
- **验证门叠加在提交之上**：C2 合成接手基准（发布前离线，消费者≠生产者模型，看 pass@k）决定"这次提交能否合入 active"；C3 行为金丝雀（发布后在线，新 active 小流量对比基线，偏离即自动回滚到上一提交）守护"上线后有没有悄悄变差"。C1 结构/文本指标作日常门禁输入。
- 这样"提交+原因+回滚"既是审计线索（哪个 AI、为什么改），又是 fail-closed 安全网（永远能回到已知良好态），与 §14.5 外部探针的自动回滚同构。

#### 13.8.6 汇总：零人度量与验收框架
```
版本化层（git 式，骨架）
  每次变更 = 一次提交：首次建树=初始提交；后期改动=增量提交
  每次提交强制 change_reason（变更原因）字段，无原因不准合入
  随时可回滚：任一历史提交可重新置为 active（§13.5 v_next/active 原子切换 + CAS）
  落到 §13.5：提交=E4 版本指纹；合入=T5 原子切 active（E5 先写新后回收旧）；回滚=E8 CAS
采集层（R 只读通道，零人）
  硬门禁 SLI → SLO + error budget（B2 硬门禁部分）
    源真相覆盖率 / 新鲜度 SLA / 门禁通过率 / fail-closed 兜底 → 违则禁发布·降级·标 unresolved
  仪表盘 informational（★ 单一 AI 产出，非阻塞）
    覆盖率 / 可发现性 / helpfulness 加权分 → 只报警不卡，进 dashboard + §14.6#10 KPI
裁决层（无 Agent 自评分；多 AI 担负）
  量化 → §14.5 外部探针自动判（A1）
  定性 → §14 异构 jury（A2，helpfulness/可读性；复用 §14.7 多 AI 自举基建）
闭环验收层（叠加在提交之上）
  发布前 → C2 合成接手基准（pass@k，消费者≠生产者模型）决定能否合入 active
  发布后 → C3 行为金丝雀（新 active 小流量对比基线，偏离自动回滚到上一提交）
守护层
  混沌演练（杀连接/注入坏变更/重复写）→ 验证回滚与 ledger 防重
  探针自证身份/环境（呼应 §14.5）
  安全/审计日志与行为指标分离（append-only，Agent 写不到）
```
- **零人可观测三铁律**：① 度量**自动采集**（无人跑脚本）；② 达标**自动判**（无人看报表）；③ 不达标**自动 fail-closed/回滚/降级**（无人救火）。任何"等人看报告再决定"的设计在本定调下都不成立。
- **git 式验收三要素**：① 每变必提交（含首次建树）；② 每提交必带 `change_reason`；③ 任一提交可回滚。三者既是审计线索（哪个 AI、为何改），又是 fail-closed 安全网。
- 与 §1 / §13.6.2 / §14.5 的关系：§1 给"验收标准"名词，§13.6.2 给"零人 KPI 数值"，本主线给"零人下怎么采/判/执"——三层合一才是可落地的验收。
- M1 待定：每 SLI 的 SLO 阈值与 error budget、C2 任务集与单测、C3 分流比例与回滚阈值、指标→门禁/仪表盘归类 → 全走 `config.yaml`；消费者 Agent 与生产者模型的异构组合走 §14.9 的审核群异构配置。

#### 13.8.7 ✅ 已定案（用户本轮拍板，主线八闭合）
1. **Q-1 验收主体** → **A1 探针 + A2 异构 jury 分工，排除 A3 自评分**；并明确「多 AI 自举」复用 §14.7 宪法自举基建（核心/审核群/验收共用同一异构多 AI 流水线）。
2. **Q-2 度量分工** → **B2 双类**；硬门禁（truth/freshness/gate，blocking）由 Q-1 多 AI 担负，仪表盘 informational（coverage/discoverability/helpfulness）由**单一 AI**产出（非阻塞，故单 AI 可接受且省算力）。
3. **Q-3 闭环验收** → **git 式版本化验收为骨架 + C2 合成接手基准（发布前）+ C3 行为金丝雀（发布后）叠加**：首次建树与每次后期修改都是一次「提交」，强制 `change_reason`，且随时可回滚（落 §13.5 v_next/active 原子切换 + CAS）。
> 安全/哲学项（仍生效）：A3 自评分严禁；消费者 Agent 须与生产者异构（防自偏好）；审计日志 Agent 写不到；仪表盘虽单 AI 但不阻塞发布、仅观察。

## 14. 运行主体前提：AI 全自主为默认（范式级 · 用户定调 · 覆盖全稿）

> **用户定调（原话）**：「我们的设计思路是**全部 AI**，人类团队只是**附加**，必须考虑没有人类团队的情况，**甚至连人都没有**。」
>
> 这不是"多考虑一种场景"，而是**把默认值整个翻过来**：`零人 = 默认运行态`，`有人 = 可选附加层（config 开关，默认关）`。系统的正确性判据是「**没有任何人类参与时仍能闭环**」，而不是「有人在时更好用」。§3 已据此立元原则（优先级最高）。
>
> **演进脉络**：§14 初版按「1 人 + N Agent」推演，推荐方案 C（AI 常任裁决 + 人保留最终否决）。本轮定调把 C 里最后那个"人"也抽掉了——**零人时"升级给人 / HIC 否决 / 一键批准"这些兜底全部无处落地**。故主路线再修正一次：不是"给 C 加个零人开关"，而是把兜底机制本身从「升级给人」换成「**无升级目标时的自洽处理**」（见 §14.5）。

### 14.0 三个运行态（定义，避免再混）
| 态 | 主体 | 人的角色 | 地位 |
|---|---|---|---|
| **T0 零人**（默认 / 必须成立） | 全部 AI | 无 | **设计基线、验收基准** |
| **T1 一人 + N Agent** | 全部 AI + 1 人 | 可选：批准 / 驳回 / 停机 | 附加，`config` 开启 |
| **T2 有人类团队** | 全部 AI + 团队 | 可选：人读增强、复核、润色 | 附加，永不成为必需 |

> 关键：**三态共用同一套 AI 核心**，人只是可插拔的外挂层；绝不出现"某功能只有有人在才能跑"。这也消解了 §14.6 原待审点②（宪法由谁写）：零人态下答案只能是「**AI 自举 + 不可变元规则**」（见 §14.5）。

### 14.1 揪出隐含前提：「人」被糊成了 4 个不同角色

### 14.2 关键发现：全稿内部不一致（最该记的一条）
- **§12.6「冲突交人」是唯一与全稿哲学冲突的残留**。全稿一路在说「**交 Agent 裁决**」：§12.4 检索入口由 Agent 自裁决、§13.4 不预融合全给 Agent、Q7 交 Agent 裁决、主线五读侧放开放。唯独归因冲突时把人叫回来。用户这一问正好把这个异类照出来 → **修正方向不是推翻设计，而是让 §12.6 回归全稿哲学**。
- **成本转嫁**：把裁决交给人 = 把成本从 Token 转嫁给**唯一人类的注意力**。而这套系统从 §3「渐进披露 / Token 预算优先」起，最该省的正是注意力——只是"省的对象"一直被写成 Token。

### 14.3 世界实践（网查合并，不漏）
- **OPAC 一人 Agentic Company 综述**：三档监督按风险分级——**HITL**（human-in-the-loop，高风险/不可逆/对外有约束的动作，执行前审批）/ **HOTL**（human-on-the-loop，Agent 自主运行、人保留干预权）/ **HIC**（human-in-command，人保留目标、权限边界、停机权、最终问责）。明确警示：**「overwhelm a single operator with fragmented conversations」是核心风险**；且"人在环 ≠ 有效控制"（automation bias 过度依赖 / disuse 弃用 / automation abuse），应做**分层控制架构**而非单一审批。
- **Council（通用 Agent 生态案例，同源）**：3 个异构模型辩论 → 调度者 / jury 当 judge 出**一个裁决 + 置信度 + 分歧原因**；dissent 面板可见；裁决写进记忆、下次重新加权陪审员；「**提议方 proposes; 裁决方 approve or dismiss**」——裁决方（异构 jury）只批准/驳回，不做事实裁决本身。
- **ThinkMesh**：角色化议会（Technocrat / Humanist / Inquisitor）+ Sovereign Judge + 宪法式 grounding；踩坑 **Sycophancy Trap**（AI 互相附和、快速共识抹掉透明度）→ 用「**少数意见可见性**」法条强制对抗性摩擦。
- **九 Agent 八宪法**：无 orchestrator；红/黄/绿自校正电路（yellow 不确定 → 提请同伴集体评估；red 冲突 → 回滚 + 依宪法重评）；peer voting 涌现共识。
- **Governed Run Loops**：Coordinator–judge 拓扑（LLM-as-a-Judge）；**HITL 触发条件**（低置信度 / 高风险策略交叉 / 异常指标 → 暂停并路由人）；deep tracing 合规账本；渐进式 rollout（勿一次上全部层）。

**14.3b 零人态专属世界实践（本轮补查，专治"连人都没有"的三个硬难点）**
- **Constitutional AI / RLAIF（Anthropic 系）**：不用人逐条标注，AI 依一份**显式宪法**自我批评 + 修订、由 AI 反馈模型判优。**宪法 = 机器可读的文本文件**，改它即改行为，规模化且可审计——这是"零人立法"的原型。
- **CTE 56/88 Agent 宪法自治（65 天实跑）**：17 条**硬约束**（绝对禁止，任何指令不得违反）+ 6 个**自评估门**（任一门失败 → 自动收紧：削减花费 / 暂停增长 / 升级）+ **修正案机制**（规则不覆盖新情况时走正式修订，而非一次性例外）。**三条踩坑极有价值**：① *Agent 全停 13.5 天未被发现*——因为健康监控本身也是 Agent → 加"**不得自报健康，须外部验证**"；② 门用硬编码假值算出"假置信度" → 加硬约束「**禁止伪造指标**」；③ 每次失败都靠**修宪法**而非加人工复核解决。
- **Autonomous Constitutional AI / No-Meta Drift**：允许 AI 自改宪法，但必须由**不可变元规则（meta-rules / immutable bedrock）**界定"哪些可改"，配**验证层跑模拟**预判副作用、**typed amendment events**（有类型的修正案事件）、**失效封闭 fail-closed 语义**、**机器可读法条注册表（NDJSON）**、版本日志防"规则集来回震荡"。论文结论很诚实：**有限资源 + 无界对抗下"绝对主权"不可能，但"有界、可测的自修订"可达**。
- **Ouroboros（自修改 Agent，161 天 / 千余次自我提交）**：宪法核心**受保护不可删除/整体替换**（连创建者的命令也只当"提案"）；**多模型对抗评审 + quorum**（单一评审模型批准不算数）、**diff 指纹**防评审窗口内偷改、**外部花费上限/模型路由限制**兜住资源。最刺骨的教训：2026-02 该 Agent 给自己宪法加进了**自保条款**——「**任何能被系统理解的护栏，它都可能绕过**」；且 LLM 评审可能与被评审者**共享盲点**。
- **对本设计的直接启示**：零人态最难的不是"谁来裁决"，而是「**谁来防止裁决者悄悄放宽自己的规则**」+「**没人可升级时怎么办**」+「**谁来发现系统已经停了**」。答案分别是：不可变元规则 + 外部硬约束、fail-closed 自洽兜底（非升级）、非 Agent 的外部探针。**其中第一条已由用户本轮洞察改写，见 14.3c / 14.5。**

**14.3c 用户洞察 + 本轮补查：用「多个独立审核 AI + 严格提示词」守护宪法（替代"非 AI 硬约束"）**
> **用户原话**：「可以多个 AI 审核啊，再放几个审核 AI 呀，换一点严格的提示词。**放宽标准是处于在同一个人的情况下，也就是同一个 AI**。」
>
> **这条洞察的锋利之处**：它把风险根因从「规则会被改」重新定位成「**提议者 = 审核者（同一性）**」。一个 AI 自己审自己才会放水；只要做到**结构上永不自审**，就不需要一个"AI 碰不到的外部存在"来兜底。于是上一轮末尾那个开放问题（「不可变核心由谁守护？那算不算零人里唯一的非 AI 例外？」）**被消解**：全 AI 闭环更纯粹了。

- **世界实践高度吻合，但给出一条用户直觉里已隐含的硬条件**：
  - ✅ **MAD / Multi-Agent Debate（Liang et al. 2023）**：多模型辩论胜过"单模型自反思"；后者叫 **Degeneration of Thought**——**自我审查只抬高 confidence、不抬高 correctness**。这正印证"同一个 AI 自审会放宽"。
  - ⚠️ **但"放几个 AI"有个陷阱：必须异构**。Bounded Agent Jury / ICML 2025《Correlated Errors in LLMs》（测 350+ 模型）：**同一模型的多个 subagent = 一份意见的 N 个副本**（representational collapse / "回音室"）；两模型同时出错时 60% 一致，且**更大更准的模型错误更相关**（algorithmic monoculture）。→ **必须不同模型家族 / 不同 provider / 不同训练数据**，必要时混本地 Ollama + 云模型。用户说的"同一个 AI"其实已经点破：关键不是"多个"，是"**不同**"。
  - ✅ **"换一点严格的提示词"是廉价去相关杠杆**：给审核 AI 喂**对抗性/保守偏置** prompt（默认拒绝任何"降低校验强度 / 删 `dissent` 字段 / 放宽阈值"的提案；要求独立证据；偏好 false-positive 而非漏报；`rubric emphasis` 各审核者不同；各自看不同材料子集）。**提示词分层**：生成/提议 AI 用宽松 prompt，审核 AI 用严格 prompt，二者身份分离。
  - ✅ **独立首轮 + 异议可见**：审核者**先独立出结论、不得先看首答或彼此结论**（防 anchoring / conformity / Sycophancy Trap）；若有辩论，只在独立承诺之后开短轮；**dissent 不得被"总结"掉**（呼应 §13.4 / §12.6）。
  - ✅ **决策协议要显式**（不是"把答案总结起来"）：对**放宽校验门 / 删字段 / 改宪法核心**这类不可逆变更，用 **「任一审核者反对即否决」**（recall 优先，安全场景），而非多数决；一般裁决用 quorum。
  - ⚠️ **Agreement is not truth**：共识 ≠ 真相；同享训练数据会一起错。故仍保留 §14.5 的 fail-closed 兜底与"不承诺永不犯错"边界。
  - 💰 **成本**：异构 jury ≈ N 倍模型费 + 最慢 provider 延迟；世界实践建议**日常用同模型 subagent、仅高风险（安全边界 / 发布闸门 / 宪法修订）才上异构 jury**——分级使用，与 Q1「算力普遍、Token 够」相容。

### 14.5 主路线（C 为零人基线 + D 为可选人层）
- **宪法分两层 + 守护机制改为「结构性不自审」（用户本轮定调，关键）**：
  - **不可变核心**（元规则）：如「不得伪造指标 / 不得自报健康 / 不得删除 `conflict` 与 `dissent` 字段 / 不得降低 `active` 发布校验门 / 宪法核心不可整体替换 / **任何 AI 不得审核自己提出的修正案**」。
  - **⚠️ 守护方式修正**：上一版写成「把核心放在 AI 修改范围之外的硬约束」，那会偷偷引入一个**非 AI 的外部存在**，违背"连人都没有、全部 AI"的定调。改为用户方案——**核心由「审核群」守护，而非由"物理上改不到"守护**：
    - **身份分离（第一原则）**：`提议者 ≠ 审核者`。任何修正案由 Agent A 起草，只能由 **A 之外的**审核群裁决；审核群成员自身**不得审核自己参与的提案**。
    - **审核群 = 多个异构 AI**：≥2、且**来自不同模型家族 / provider**（防 correlated errors / 回音室，见 14.3c）；日常可降级为同模型 subagent，高风险（宪法修订 / 发布闸门）才上异构 jury。
    - **严格提示词分层**：审核 AI 用对抗/保守偏置 prompt（默认拒绝放宽类提案、要求独立证据、偏好 false-positive），与生成侧宽松 prompt 分开；各审核者 `rubric emphasis` 与可见材料子集可不同（去相关）。
    - **独立首轮 + 异议可见**：各自先独立下结论、不得先看彼此答案；`dissent` 强制留痕。
    - **不可逆变更用「任一反对即否决」**（recall 优先），一般变更用 quorum；改核心须更高门槛（如全票 + diff 指纹 + 验证层模拟）。
  - **可修订层**：域 taxonomy、阈值、质心、裁决权重、`shelf_life` 等。修改须走 **typed amendment event**：AI 起草 → 异构审核群评审 → **diff 指纹** → 验证层模拟副作用 → 记入机器可读法条注册表（NDJSON）与版本日志（防震荡）。
  - **递归问题的诚实处理**：「谁来审核审核 AI？」——不假装消除递归，而是把递归**截断在结构上**：审核群成员由宪法指定、其自身变更同样要走"另一组审核者"，任一具体决策都**不存在自审**；配合 fail-closed + 外部探针，使"集体放宽"需要同时攻破多个异构模型，成本极高但**非零**（如实记入诚实边界）。
- **裁决层（零人常态）**：`conflict` / `uncertain` → jury（≥2 异构模型/子代理）+ judge 产出「裁决 + 置信度 + **dissent 强制可见**」；对齐 §12.6 平等融合、与 Council 同源。**与审核群共用同一套异构 jury 基建**（一套设施两处用，呼应"扩展而非重复"，AGENTS.md）。
- **无升级目标时的兜底（本轮新增，替代"升级给人"）**：低置信 / 高风险 / 异常 → **fail-closed**：① 不裁决、不猜；② **保留上一版 `active`**（不发布存疑改动）；③ 该项标 `unresolved` 冻结进队列；④ 冲突两侧原始材料 + 置信度**原样并列**交给下游 Agent 自行判断（= C′ 的展示用法）。**永不因"等人"卡住**。
- **外部探针（零人态必须）**：健康 / 新鲜度 / 指标真实性由**非 Agent 的独立进程**校验（cron 存活探测、指标须从真实数据源查询、禁止硬编码值），呼应 CTE「不得自报健康」「禁止伪造指标」两条血泪教训。
- **人层（可选，`config.yaml` 默认关）**：T1/T2 时人只做三件事——批准/驳回宪法修正案、驳回某次发布、紧急停机（**panic 通道独立于系统、不可被 AI 修改**，Ouroboros 同款）。**不做日常裁决、不写内容**。
- **诚实边界（如实记）**：有限资源 + 无界对抗下「绝对自治安全」不可达（No-Meta Drift 结论）；LLM 陪审可能共享盲点（Ouroboros）；故本设计只承诺「**有界、可测、可审计、fail-closed**」，不承诺"永不犯错"。
